# PowerPulse — Phased Implementation Plan

> Standing context (architecture, verification ethos, structure, rules) is in `PROJECT_CONTEXT.md`. Read it first.
> This document is the work plan: ordered tasks, deliverables, and exit criteria.

**Conventions**
- Each task has an ID (`P1-xx`, `P2-xx`). Use it in commit messages.
- Every task ends with: tests passing via `make`, documentation written, README updated if user-visible.
- `[ ]` items are exit criteria; tick them as they are met.

---

## Overview

| Phase | Tasks | Milestones |
|---|---|---|
| **Phase 1 — Foundation and UART end to end** | P1-01 … P1-13 | **A:** core-less bus + UART verified. **B:** VeeR running software over the bus, UART verified end to end |
| **Phase 2 — Custom IPs** | P2-00 … P2-07 | **C:** each IP verified standalone and integrated. **D:** full activity-management scenarios and coverage closure |

```
Phase 1:  repo → config → make/run-dir → VeeR → interconnect → adapters → UART → mem/top → TB infra
          → Milestone A (core-less) → sw flow → Milestone B (core-in-loop) → regression + docs

Phase 2:  Timer/GPIO + hooks → register-slave template → HAP → PPMC → AWEC
          → system scenarios → coverage closure → final docs
```

# PHASE 1 — Foundation and UART end to end

**Goal:** a reproducible repository where the VeeR core talks to UART through a generated, parameterised AXI interconnect, verified by both bus-level integration tests and real software, all driven by simple make commands.

**In scope:** repo and git hygiene, config system, make flow, VeeR integration, interconnect generation, width adapters and protocol bridges, memories, SoC top, UART, test infrastructure, software flow, tests, README, docs.

**Out of scope:** the custom IPs' RTL (slots reserved only), physical power gating of any kind.

## P1-03 — Makefile and test-aware run directory

**Steps**
1. Build the make interface from `PROJECT_CONTEXT.md` §5: `run`, `wave`, `regress`, `list`, `hex`, `clean`, `clean-all`, `help`; optional `SEED`, `CONFIG`.
2. Implement the **shared build** in `sim/build/` (rebuilt only when RTL/config changes) and **per-test run folders** in `sim/runs/<test>/` containing `sw/`, `logs/`, `waves/`, a command record and a `result` file.
3. Implement `sim/latest` pointing to the last run; omitting `T` reuses the last test.
4. Implement **test discovery by folder** and a per-test **settings file** with: type (unit / integration / software), purpose (one line), timeout, plusargs, group tags (e.g. `smoke`, `uart`, `adapter`), expected result.

7. Seeded runs go to `sim/runs/<test>_s<seed>/`.

**Deliverables:** Makefile, helpers in `tools/`, `docs/make_flow/`.

**Exit criteria**
- [ ] `make help` and `make list` work on a fresh clone.
- [ ] A trivial placeholder test runs through `make run` and produces the full run folder.
- [ ] Re-running without changes rebuilds nothing.
- [ ] `make wave` opens the correct run's waveform in Verdi.

**Steps**

**Exit criteria**

## P1-05 — Interconnect generation

**Steps**
1. Wrap the existing Python generator around the config. Inputs: master list, slave list with map and protocol. Outputs: interconnect RTL, C memory-map header, SV memory-map package/include, human-readable register/memory-map table for docs.
2. Implement the **map checker** (run as part of generation, fails the build on violation):
   - no overlapping ranges
   - alignment and size rules
   - no overlap with core-internal regions
   - disabled slots resolve to a stub, never to nothing
3. **Default slave:** unmapped addresses return a decode error (DECERR) with correct handshakes — never hang.
4. **Reserved slots:** HAP/PPMC/AWEC/Timer/GPIO routed to the stub slave while disabled; enabling one is a config flag only.
5. Multi-master arbitration among IFU, LSU and SB per configured policy; document it.
6. Mark all outputs "generated — do not edit".

**Deliverables:** generator updates, map checker, `docs/interconnect_generator/` (inputs, outputs, how to add a slave, arbitration, error behaviour).

**Exit criteria**
- [ ] `make gen` regenerates everything deterministically.
- [ ] Map checker catches deliberately introduced overlaps (verified once, then kept as a unit test of the tool).
- [ ] Adding a dummy slave via config alone produces a working slot.

## P1-06 — Width adapters and protocol bridges

**Why:** VeeR's AXI ports are 64-bit; the interconnect is 32-bit. VeeR issues AXI4; some slaves are AXI4-Lite.

**Components**
1. **Downsizer (64 → 32)**, one per core master:
   - splits 8-byte accesses into two 32-bit beats
   - selects the correct lane for narrower accesses from address and byte strobes
   - merges two read halves into one 64-bit response; returns the **worse** error of the two beats
   - preserves IDs; handles bursts per the core's actual behaviour (documented)
   - parameterised on both widths, reusable
2. **AXI4 → AXI4-Lite bridge**, instantiated only where config requests it: handles IDs and any burst-to-single conversion.

**Unit tests (core-less, using the AXI master model)**
- byte, halfword, word and doubleword reads and writes at every legal alignment
- byte-strobe correctness on writes
- error response propagation (SLVERR/DECERR), including an error on only one of the two split beats
- ID preservation, back-to-back and outstanding transactions
- randomised ready/valid backpressure with logged seeds
- reset in the middle of a transaction

**Deliverables:** adapter/bridge RTL, unit benches, `docs/width_adapters/`.

**Exit criteria**
- [ ] All adapter unit tests pass with multiple seeds.
- [ ] Protocol checkers report no violations on either side.
- [ ] A deliberately broken lane-select is caught by the tests (check-can-fail sanity).

## P1-09 — Verification infrastructure

**Components**
- **AXI master model** (parameterised data width — used at 64 and 32): single and burst transfers, narrow transfers, strobes, randomisable ready/valid delays, seed-controlled.
- **AXI protocol checkers** (assertions) attachable to any master/slave port; always enabled.
- **UART testbench model**: transmits bytes into the DUT's RX, decodes the DUT's TX, checks framing/baud; supports error injection (bad stop bit).
- **Status device** (from P1-08) and simple scoreboard/reporting utilities with uniform PASS/FAIL messages the regression runner parses.
- Clock/reset generators driven by config.

**Deliverables:** `tb/common/`, `docs/tb_infrastructure/` (how to write a new test).

**Exit criteria**
- [ ] A new unit test can be written using only `tb/common/` components and the settings file.
- [ ] Checkers shown to fire on injected violations.

# PHASE 2 — Custom IPs

**Goal:** implement HAP, PPMC and AWEC as memory-mapped AXI slaves in their reserved slots, verify each standalone and integrated, then verify the complete activity-management behaviour end to end.

**Order rationale:** HAP first (PPMC consumes its idle indication), PPMC second (central state machine), AWEC last (needs both and the wake sources).

---

## P2-00 — Prerequisites: Timer, GPIO and power-management hooks

**Steps**
1. Integrate **Timer** and **GPIO** (mandatory components) into their reserved slots with the same flow as UART (wrapper if needed, config entry, docs, register tests).
2. Add an **enable / clock-enable input** to every peripheral the PPMC will control (UART, Timer, GPIO as chosen), default-enabled so Phase 1 behaviour is unchanged. Document exactly what "reduced activity" means for each (RTL enable gating only).
3. Define each peripheral's **activity indication** (what the HAP observes) and **wake source** (what the AWEC observes): UART RX activity, GPIO edge event, Timer compare event.
4. Wire peripheral/IP interrupt lines to the core's interrupt controller as needed for software status handling.
5. Re-run all Phase 1 regressions: no behaviour change when enables are tied active.

**Exit criteria**
- [ ] Timer and GPIO have register tests and software tests equivalent to UART's.
- [ ] Phase 1 regression remains fully green.
- [ ] Activity, enable and wake signals are listed in one documented table.

---

## P2-01 — Reusable register-slave template and IP documentation kit

**Steps**
1. Create an AXI4-Lite register-slave template in `rtl/common/` so each IP only writes register logic, not handshaking.
2. Define register conventions: access types (RO, RW, W1C, W1S…), reset values, reserved fields, write-ignore rules.
3. Create the per-IP spec template (overview, interface, register map, state machines, corner cases, test plan) so the spec is written *before* RTL.

**Exit criteria**
- [ ] Template verified by a unit test using an example register set.
- [ ] Spec template ready and used by all three IPs.

---

## Per-IP definition of done (applies to P2-02, P2-03, P2-04)

1. **Spec first:** register map, ports, parameters, state machines, corner cases, written in `docs/<ip>/` and reviewed.
2. **RTL:** synthesizable, parameterised, uses the register-slave template.
3. **Unit testbench:** self-checking, directed plus randomised, assertions for protocol and internal invariants.
4. **Integration:** slot enabled via config only; address decode, adapters and reset behaviour verified through the interconnect.
5. **Software driver and tests:** register-level driver in `sw/common/`, software tests exercising the IP through the core.
6. **Coverage:** functional coverage points defined from the spec; results recorded.
7. **Documentation:** full standard (diagram, interface, registers, behaviour, how to run, verification summary, open issues).
8. **Regression:** the IP's group joins `all`; everything green.

## P2-02 — HAP (Hardware Activity Profiler)

**Spec topics:** monitored activity inputs and selection mask; per-channel inactivity counters; programmable idle threshold; counter reset on activity; idle indication generation and clearing; status and configuration registers.

**Unit tests (examples):** counter increments only when idle; reset on each activity pulse; threshold boundary (N-1, N, N+1); threshold changed while counting; mask enable/disable; simultaneous activity on several channels; register reset values and access types; back-to-back configuration writes.

**Assertions (examples):** idle never asserts before threshold; counter never advances while activity present; idle deasserts after activity.

**Software tests:** configure threshold and mask, generate and withhold peripheral activity, read idle status.

---

## P2-03 — PPMC (Peripheral Power Management Controller)

**Spec topics:** states **ACTIVE / IDLE / LOW-ACTIVITY** per controlled peripheral; transitions driven by HAP idle indications, AWEC wake requests and software policy; enable / clock-enable outputs; software-visible current state; policy registers (which peripherals are managed, whether transitions are automatic or software-gated); behaviour on simultaneous idle and wake.

**Unit tests (examples):** every legal transition and each trigger; illegal/ignored transitions; wake during IDLE and during LOW-ACTIVITY; wake arriving in the same cycle as idle; policy disables automatic entry; per-peripheral independence; software forcing a state; state/enable outputs consistent in every state; reset state.

**Assertions (examples):** enables never glitch outside defined transitions; LOW-ACTIVITY always exited by wake or software; state register always legal.

**Software tests:** read state, change policy, observe enable effects on a managed peripheral.

---

## P2-04 — AWEC (Autonomous Wake-Up Event Controller)

**Spec topics:** wake sources (UART RX activity, GPIO edge, Timer compare); per-source enable mask; event detection and capture; wake-source identification register; wake-up request to the PPMC; acknowledgement and clearing; behaviour for events during masked state and for repeated events.

**Unit tests (examples):** each source individually; masked source ignored; multiple simultaneous sources and identification; event arriving while a previous one is un-acknowledged; clear/acknowledge behaviour; edge vs level semantics per spec; glitch/short-pulse handling as specified.

**Assertions (examples):** a valid enabled event always produces a wake request; no request without a captured event; captured source stable until acknowledged.

**Software tests:** enable sources, trigger each, read identification, acknowledge, verify no polling loop is needed.

---

## P2-05 — System integration and scenarios

Enable all three IPs through config and run full scenarios with the core, peripherals and testbench stimulus.

**Scenario list (group `power`)**

| Scenario | Sequence verified |
|---|---|
| `power_idle_entry` | peripheral stops being used → HAP idle → PPMC enters LOW-ACTIVITY |
| `power_wake_uart` | in LOW-ACTIVITY, testbench sends UART byte → AWEC → PPMC restores → software receives byte intact |
| `power_wake_gpio` | GPIO edge wakes the managed peripheral |
| `power_wake_timer` | Timer compare event wakes the managed peripheral |
| `power_full_sequence` | monitoring → idle → LOW-ACTIVITY → wake → restore → software status handling, end to end |
| `power_multi_peripheral` | several peripherals managed independently |
| `power_race_wake_idle` | wake event during the idle→low-activity transition |
| `power_back_to_back` | repeated idle/wake cycles |
| `power_policy_change` | thresholds/masks/policy reprogrammed at run time |
| `power_no_data_loss` | no byte/event lost across a wake (UART RX especially) |

**Exit criteria**
- [ ] All scenarios pass across multiple seeds.
- [ ] Waveforms of the full sequence captured for the project deliverables (annotated, simple and clean).

## P2-06 — Verification closure

**Steps**
1. Review assertion coverage of every state machine and handshake.
2. Collect and **merge functional and code coverage** across the full regression; set targets in the verification docs.
3. For every uncovered item: write a test or justify in writing.
4. Run the full regression across a seed set; record results.
5. Negative and stress tests: illegal register writes, reset during transitions, extreme thresholds (0, max), rapid reconfiguration.

**Exit criteria**
- [ ] Coverage targets met or each gap justified.
- [ ] `make regress G=all` green across the agreed seed set.
- [ ] No open protocol-checker violations.
